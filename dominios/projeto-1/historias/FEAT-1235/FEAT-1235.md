# Detectar e bloquear uso de sessão Redis expirada

Descrição resumida
- Evitar processamento de mensagens associadas a sessões do Redis cujo TTL expirou, impedindo reutilização de `client_id` e `conversation_id` em sessões diferentes.

Objetivo
- Fazer com que o serviço que consome a lib do Redis detecte sessão expirada e retorne indicação de "sessão expirada" ao chamador/frontend, para que a conversa seja reiniciada e novos IDs sejam gerados.

Critérios de aceitação (Gherkin)
- Cenário: Sessão válida é processada normalmente
  Dado que o usuário envie uma mensagem
  E a sessão Redis esteja válida
  Quando a requisição for processada
  Então a mensagem segue o fluxo normal

- Cenário: Sessão expirada interrompe processamento
  Dado que o usuário envie uma mensagem
  E a sessão Redis esteja expirada
  Quando o serviço verificar a sessão
  Então o processamento da mensagem é interrompido
  E a requisição retorna indicação de sessão expirada

- Cenário: Frontend reinicia conversa após expiração
  Dado que o frontend receba o status de sessão expirada
  Quando identificar a expiração
  Então deve reiniciar a conversa
  E gerar novos `client_id` e `conversation_id`

Dependências
- Lib externa que gerencia Redis (INFORMADO).
- Serviço(s) que consomem a lib do Redis (INFORMADO).
- Frontend responsável por resetar a conversa (REQUISITO INFORMADO).
- Detalhes do contrato (HTTP status/código/payload) entre backend ↔ frontend: PENDENTE.

  - Implementar verificação de sessão antes do processamento, retornar status/session_expired.
  - Ajustar ou ampliar a lib do Redis se necessário — PENDENTE.
  - Implementar tratamento para condição de corrida (TTL expira entre verificação e processamento) — PENDENTE.
- QA:

  - Testes de regressão para outros consumidores da lib.
- Docs:
  - Atualizar especificação do contrato (status HTTP, código, payload) indicando "SESSION_EXPIRED".
  - Documentar comportamento esperado no frontend (reset e geração de IDs).

Riscos
- Reutilização de `client_id` e `conversation_id` em sessões diferentes (INFORMADO).
- Possível impacto em outros consumidores da lib Redis se o contrato mudar (PENDENTE).
- Condição de corrida entre verificação do TTL e processamento, podendo causar falso-positivos/negativos (PENDENTE).
